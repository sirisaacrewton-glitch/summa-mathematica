## 0. 全体像

* **何をしているか**：数学を体系化した静的サイト「Summa Mathematica」（日本語の副題「数学大全」。2026-10-07 に「数学ノート」から改名）を作っている。
  * 1 ページ ＝ 1 つの HTML ファイル（専門書の 1 節弱）。
  * 原稿は Markdown + LaTeX で書き、番号・目次・相互参照・検索索引はビルドと表示時に自動で付く。
* **作業は Claude だけで完結させる**。
  * 教科書は、PDF から文字だけ取り出したテキスト（非公開リポジトリ `math_books` の `_text/`）を、**必要な行範囲だけ**読む。
  * 訳語は、日本語の本のテキストで使われ方を確かめる。
* **1 トークで 1〜2 ページ**を書く。何を書くかは `PROGRESS.md` の「次の作業」で決まる。
  * ユーザーが「次の記事を書いて」と言ったら、その先頭を実行する。
  * 「IV-03 を書いて」のように ID で指定されたら、その行を実行する。
  * 「次は〇〇の本をやる」と言われたら、第 10 節の準備をする。
* **トークン節約の決まり**：
  * 過去のトークを読まない。
  * 他のページを全文読まない。`labels.js find/uses` と `grep -n` で要る所だけ見る。
  * `AUTHORING.md` は全部読まない（必要な節だけ grep）。
  * PDF を画像で読まない（図が必要なときだけ、そのページだけ）。
  * サブエージェントを並列で立てない（利用上限に達して止まった前例がある）。
  * 記事だけの変更ならスクリーンショットは撮らない。

## 2. 本の読み方

* 本のテキストと索引は、本棚フォルダの `_text/` にある（どの本のどれかは `PROGRESS.md` の資料表）。
  * `xxx.txt`：PDF から取り出した本文（OCR 由来で記号が崩れていることがある。意味を読み取って使う）。
  * `xxx.index.txt`：章・節・定義・定理などの行番号一覧。
* **手順**：
  1. 担当ページの範囲の行番号を、`PROGRESS.md` の表と索引で確かめる。
     ```
     awk -F: '$1>=5359 && $1<5678' "<洋書>/_text/kunen1980.index.txt"
     ```
  2. 本文をその範囲だけ、300〜400 行ずつ読む。
     ```
     sed -n '5359,5700p' "<洋書>/_text/kunen1980.txt"
     ```
  3. 章末の演習は索引の `EXERCISES` の行から探し、関係するものだけ読む。
* **新しい本を使うとき**：
  ```
  bash _claude/bin/booktext.sh "<PDF のパス>" "<本棚>/_text/<略称>.txt"
  ```
  * テキストと索引ができるので、`PROGRESS.md` の資料表とページ割り当て表に追加する。
  * 1 回の実行は約 3 分まで。長い本は `[開始ページ 終了ページ]` を付けて分ける。
  * **本のテキストはサイトのフォルダに置かない**（公開時に一緒に出てしまうため）。
* 図や、OCR が崩れて読めない数式がどうしても必要なときだけ、そのページを画像にして見る（例 `pdftoppm -f 120 -l 120 -png`）。

## 4. 記事を 1 本書く手順

1. **範囲を決める**：`PROGRESS.md` の該当行（ファイル名・題・本の節・行範囲）。
2. **本を読む**（第 2 節の方法）。定義・定理・補題の流れと依存関係を、自分用に箇条書きでメモする（出力には出さなくてよい）。
3. **既存のラベルと予定ラベルを調べる**：
   ```
   node tools/labels.js planned set:        # 他ページから予約済みの未執筆ラベル
   node tools/labels.js find <語>           # 関連する既存の定義・定理
   ```
4. **ラベル計画**：主要なラベルを決める。
   * `planned` に出た予定ラベルで、このページが扱うものは、**その名前のまま定義する**（既存ページからのリンクが自動でつながる）。
   * 新しいラベルは第 5 節の命名規則に従う。
5. **訳語**を第 3 節で確定する。
6. **書く**：`template.html` の型と第 6 節の内容規則に従う。
   * 本の文章は訳さず、写さない。
   * 本が省略した証明はすべて埋める。
   * 前のページの記法は `grep -n` で合わせる。
7. **書き込む**：クラウド側の clone の中で、`Write` / `Edit` で記事を直接書く。
   * 小さな修正は `Edit` か `python3` の読み込み→置換→書き戻しで行う。ツール出力から本文を打ち直さない。
   * ユーザーのコンピュータのサイトのフォルダは、もう編集しない（2026-10-07 時点の古い写し）。
8. **検査**：`node tools/build.js --check --only <記事のフォルダ>` を実行し、自分のページの問題をすべて直す。
   * KaTeX エラー、未閉じの環境、ラベル重複、未定義参照を直す。
   * 表示名のない予定ラベルには `\ref[表示名]{…}` を付ける。
9. **自己検証**（ユーザーの要望。省略しない）：
   * 反例がないか。
   * 引用した定理の前提を満たしているか。
   * 循環論法になっていないか：依存順で前のものだけを証明に使う。後のページへの参照は intuition・supplement の中だけにする。
   * 公理の使用（ZF / ZF⁻ / AC など）の記述が正しいか。
   * 不確かな事実・文献がないか。
   * 新しく定義した語が、ビルドの「文脈で意味が変わるかもしれない用語」に出ていないか（§5.2）。
10. **本ビルド**：`node tools/build.js --quiet`。そのあと `node tools/labels.js activate <接頭辞>` で、名前表示の参照のうち番号表示にすべきものを直し、もう一度ビルドする。
11. **記録と push**（次のトークのために必ず行う）：
    * `PROGRESS.md`：その行の状態を「完了」にし、「次の作業」を更新し、完了ログに 1 行足す。
    * `TERMS.md`：新しく決めた訳語を足す。
    * 判断を保留した点は「ユーザーの判断待ち」に書く。
    * `git add -A && git commit -m "<ID>: <題>"` → `git push`。push しないとクラウドの作業はセッション終了で消える。
    * commit 前に `git diff --cached | grep -E "/Users/|Downloads|\.pdf"` で、パスが混ざっていないか確かめる。
12. **報告**（短く）：
    * 書いたファイルと主なラベル。
    * 本から変えた点（補った証明・直した誤り）。
    * 確認しきれずに残した点。

### 5.2 参照の書き方
* 他ページへのリンクは**ファイルパスではなく必ずラベル**で書く。ページを移動・改名しても、ビルドし直すだけでリンクが保たれる。
* 参照コマンド：

  | 書き方 | 表示 |
  |---|---|
  | `\ref{L}` | 定理 5.3（他分野なら「位相 定理 5.3」） |
  | `\eqref{L}` | (5.3) |
  | `\nameref{L}` | タイトル |
  | `\fullref{L}` | 定理 5.3（タイトル） |
  | `\numref{L}` | 5.3 |
  | `\ref[表示名]{L}` | 表示名をリンク文字にする |
  | `\tref{L}` | 定理 5.3（refname があっても種類と番号で表示）。ページ・節を指すときは「様相 §4」（分野の略称と § 番号） |
  | `\see{L}` | 表示は `\ref{L}` と同じ。**論理の依存ではない案内**（「〜は後で扱う」「詳細は〜」「〜と同じ約束」）に使う。前提・ロードマップ・依存の検査に数えない |

* **名前で表示する定理（refname。2026-10-22 ユーザー指示）**：次のものは定義に `refname="名前"` を付け、`\ref{L}` を番号でなく名前で表示する（項目参照は「正規性 3」。ホバーで番号と所在が見える）。番号は覚えられないが名前なら 2 回目以降はリンクを開かずに済むため。**名前は長くてよいので、分野を知らなくても何の定理かすぐわかるものにする**（同名があれば「群の準同型定理」「シローの定理（個数）」のように区別）。
  * 有名な定理：人名の定理や「中国剰余定理」「選択公理」など標準的な名前のもの。どこから参照しても名前で表示。
  * **一番下のフォルダ（系列）の中で 10 回以上参照される定理・補題**：`refscope="field"` も付ける。同じ分野（ディレクトリの第 1 階層）の中では「定理：正規性」のように種類（定義した環境の種類）と名前、他の分野からは「分野 定理 番号」で表示（2026-10-22 ユーザー指示。有名な定理は名前だけ）。執筆で参照回数が 10 回を超えたら付ける。
  * サイト内で付けた説明的な題でも、上の条件を満たし内容がすぐわかる名前なら付けてよい。同名が多い一般的な名前（「不動点定理」「構造定理」）はそのまま使わない。
  * refname をもつ項目の名前を本文に書いた直後に参照するとき（「**原始元定理**（…）」「ツォルンの補題は …」）は `\tref{L}`（種類と番号）を使って名前の重複を避ける。「名前（\ref{L}）」とは書かず `\ref{L}` だけにする。
  * **名前を二度出さない（2026-10-22 ユーザー指示）**：ページ・節への `\ref` はページ・節の題で、refname をもつ定理への `\ref` は名前で表示される。同じ文の中に同じ名前を本文でも書くと二度出る（「ヘネシー–ミルナーの定理（ヘネシー–ミルナーの定理）」）。「名前（`\ref{L}`）」は `\ref{L}` だけにし、名前を本文に残すときは `\tref{L}` にする。ビルドが「参照の表示名…が同じ文に二度出る」と報告する（括弧の外の「。」までを同じ文とみる。数式 `$\mathsf{S5}$` の中の名前も数える）。
  * **依存の向きを守る（2026-10-22 ユーザー指示）**：主張と証明が使えるのは、同じ系列の前のページ、前提知識（`_meta.json` の `prereq`）の系列、その祖先の前提知識だけ。後ろのページや他の系列の結果に触れるだけなら `\see`。問題で後ろの結果を使うときは「後のページの〜を先取りしてよい」と問題文に書く。ビルドが次を報告する：定理単位の輪・ページ単位の輪・同じ系列の後ろのページへの依存（問題として数える）、前提知識にない系列への依存（件数だけ。`DEP_REPORT=1 node tools/build.js` で一覧）。2 か所以上で使う系列は `prereq` に足す（使う範囲が一部なら `"from"`/`"to"` で § を指定）。逆向きの依存（系列 A が B を、B が A を使う）は、使う結果をそれを示す系列へ移すか、別証明にする。
  * **別証明（2026-10-22 ユーザー指示）**：`::: proof 別証明（〜）` のように題名を「別証明」で始めると、その中の参照は主証明の前提に数えない（役割 a）。主証明は前提の少ない（その系列の中で完結する）ものにし、強い定理や他分野の道具を使う証明は別証明に回す（例：中間値の定理は上限の公理で示し、連結性による証明は別証明。GL のカノニカルモデルの反射点は有限の鎖で示し、算術的解釈による証明は別証明）。直前に補題などを挟んで主張から離れた別証明には `{of="主張のラベル"}` を付けて、どの主張の証明かを明示する（例：`::: proof 別証明 2（…） {of="logic:prop-compactness"}`）。ビルドは別証明ごとに使う結果を site-index.js の altDeps に記録し、学習ルートで「証明のルート」を選べるようにする（Pro では理解済みの項目から見て未習得の前提が最も少ないルートを自動で選ぶ）。主要な定理には、前提の違う別証明を少しずつ足していく（現在：命題論理のコンパクト性 3 通り、中間値の定理、GL のカノニカルモデル、コーシーの定理、代数学の基本定理（複素解析 ⇄ ガロア理論））。
  * **ステップの見出しと主張を重ねない**：`**Step 2（NP 困難）.** 【主張：…は NP 困難である】` のように見出しの括弧が主張と同じことを言うなら括弧を外す（`**Step 2.**`）。括弧は場合分け以外の、主張にない情報（「はさみうち」「証人を選ぶ」など）だけに使う。
  * **理由に「明らか」だけを書かない**：段階表示では理由を開いて確かめるので、「定義から明らか」「自明」で済ませず、どの定義・どの条件からどう従うかを一言で書く。

* **項目参照（必須。2026-10-22 ユーザー指示）**：定理・補題などの番号つきの項目を参照するときは、**必ず** `\ref{L.K}` と書く（「\ref{L} の 2」「\ref{L} (2)」とは書かない。プレビューが定理全体になり画面を無駄に占めるため）。K は項目のキー：
  * 環境の直下の番号つき箇条書き「1. …」→ 番号（`\ref{L.2}`。表示「定理 5.3 の 2」）
  * 箇条書き「- (a) …」や段落の頭の「(1) …」「**(i) …**」→ 括弧の中（`\ref{L.a}`。表示「定理 5.3 の (a)」）
  * 並べるときは `\ref{L.1}・\ref[2]{L.2}`、`\ref{L.a}⇒\ref[(b)]{L.b}`。その項目がなければビルドが警告する。
  * **新しく書く定理の項目は、文中に「(a) …、(b) …」と並べず、必ず上のどれかの形（箇条書き）にする**（参照できるように）。
  * プレビュー（ホバー・スマホのシート）は「共通の前提（最初の項目より前）＋その項目」だけを出す。同じカード（環境）の中の同じラベルの項目参照はまとめて出すが、証明が「**Step 1.**」「**(2)**」など太字で始まる段落で区切られているときは、その区切りの中だけでまとめる。「全体を表示」で全文になる（site.js の itemsOnly・itemScope）。
* **未執筆の記事への参照**は `\ref[表示名]{予定ラベル}`。表示は「表示名（未執筆）」になり、そのラベルが定義された時点でビルドすれば自動でリンクになる。表示名がないとビルドが警告する。
* 1 つのディスプレイ数式に `\label` は 1 つまで。番号は「節番号.通し番号」で、定理類と式が 1 つのカウンタを共有する。

### 5.3 よくある作業の手順（すべてサイトのルートで。最後に必ず `node tools/build.js --quiet`）

| したいこと | 手順 |
|---|---|
| ラベルの重複を直す | ビルドが「ラベル重複」を報告する。**新しく書いた側**の定義と、そのページ内の参照を手で別名に直す（`rename` は同名の全箇所を変えるので、重複の解消には使わない）。 |
| 未執筆リンクを有効にする | 予定ラベル（`planned` で確認）と**同じ名前**で定義してビルドするだけ。予定ラベルの名前が内容に合わなければ、先に `rename` で直してから定義する。 |
| 名前表示のリンクを番号表示にする | `node tools/labels.js activate <接頭辞>` で一覧 → 文脈を見て `--apply`、または手で `\ref` / `\fullref` / `\nameref` に直す。 |
| ラベルを改名する | `node tools/labels.js rename <旧> <新> --dry` で影響箇所を確認 → `--dry` なしで実行する。定義 `{#…}`・`\label{…}`・各種 `\ref`・`restate ref="…"` が全ページで張り替わる。新ラベルが既に定義済みなら中止される。 |
| ラベルの使用箇所を調べる | `node tools/labels.js uses <ラベル>` |
| ページの移動・改名、順番の入れ替え | ファイル名（`NN-slug.html`）を変えてビルドするだけ。節番号・定理番号は自動で振り直され、ラベル参照はそのまま有効。 |
| 分野フォルダ・系列フォルダを追加 | 第 8.1 節の規則でフォルダを作り `_meta.json` を置く（下の例）。分野フォルダの `_meta.json` には `field`（MSC 2 桁）を書く。そのあと**第 8.2 節の確認リスト**をすべて行う。 |
| 分野の見せ方（大分野・見出し・階層）を変える | **第 8.2 節の確認リスト**をすべて行う（表示は複数の場所で別々に作られているので、一か所だけ直すと食い違う）。 |
| 参照がないが予定として残したいラベル | `labels.json` に `"status": "planned", "title": "…", "manual": true` を手で追加する。 |

`_meta.json` の例：

```json
{ "id": "set-combinatorics", "title": "無限組合せ論", "en": "Infinitary Combinatorics", "abbr": "無限組合せ",
  "description": "概素族、マーティンの公理、…（Kunen 第 II 章に対応）", "msc": "03E05, 03E50",
  "prereq": [ { "dir": "set-basics", "from": 1, "to": 13, "note": "順序数・基数・選択公理・共終数" } ] }
```

* `aliases`（任意。2026-10-23）：検索で分類名として引く別名の配列（例：代数的位相幾何学に `["代数トポロジー", "位相幾何学"]`）。分類（大分野・分野・系列）は名前・英語名・別名で検索結果に出て、概要ページへ飛べる。
* `id`：系列フォルダ（最下層）の名前。前提知識の参照先に使う。フォルダを移動・改名しても変えない。
* `prereq`：前提知識。フォルダの概要ページ（index.html）の「前提知識」に、リンク付きで「集合論 › 基礎事項 §1〜§13（…）：補足」と表示される。
  * `dir` は参照先の系列の `id`。`from` / `to` は § 番号かページラベル。両方省くと系列全体、`to` を省くと 1 ページだけ。
  * 未執筆の系列やページも指定できる（「未執筆」と表示され、書かれると自動でリンクになる）。未知の `id` はビルドが警告する。

## 6. 記事の内容規則（ユーザーの要望。厳守）

* **形式**：日本語、である調。1 ページは専門書の 1 節弱で、原稿は 8,000〜25,000 字が目安。長くなりすぎるときはページを分け、`PROGRESS.md` の表を直す。
* **冒頭**：短い導入文と「## 記法と定義の確認」（`::: notation`）を置く。前ページまでの定義を `\ref` で確認し、議論する体系（ZF か ZFC か、など）を書く。
* **本の扱い**：教科書の流れは参考にするが、**翻訳・転載しない**。自分の言葉で書き直す。
  * 本の番号は原稿に書かない。番号はサイトが自動で振る。出典として「Kunen 第 II 章 演習 11」のように書くのはよい。
  * 本が「明らか」「□」「読者に任せる」で済ませた証明はすべて埋める。必要なら補題を足す。
  * 重要な演習問題は本文に取り込んでよい。
* **証明**：
  * Step-by-step で、途中式や論理展開を省略しない。
  * 過度に強力な定理（over power）を使わない。
  * **循環論法を避ける**：証明で引用してよいのは、依存順で前に証明した結果か、`fact` として明示した既知の結果だけ。
* **ステップの主張（2026-10-22 ユーザー指示）**：「**Step N（…）.**」の直後に `【主張：…】` でそのステップの主張を書く（例：`**Step 3（$\Box$ の ⇐）.** 【主張：$w'\models\Box B$ ならば $w\models\Box B$】 $w'\models\Box B$ とし…`）。本文では主張が独立した行になって「主張」の札がつき、続く理由の頭に「理由」の札がつく（主張で段落が終わるときは「理由」の札は出ない）。証明の段階表示では理由を伏せて主張だけを見せ（読者が自分で確かめてから開く）、過ぎたステップの主張を一覧で残す。流れ全体を考えさせるのは証明パズル（ゲーム）の役目で、こちらは「流れは提示し、細かい主張を自分で確かめさせる」ためのもの。新しく書く証明には付け、既存の証明には順に足す。**ステップの分け方**：1 ステップは 3〜4 行で書ける内容を目安にする。**読者が確かめる価値のある主張だけをステップにする**（2026-10-22 ユーザー指示：細かすぎない）。定義をなぞるだけの場合分け（命題変数・$\bot$・$\to$ の場合など）、対称な議論の片方、最後の当てはめ（「$\ell=0$ とすればよい」）、補集合をとるだけの系は独立のステップにせず、隣のステップにまとめるか、ステップの外の締めの段落にする。ステップが 3 つ未満の証明は段階表示の対象にならない（短い証明はそれで良い）。定義に従って確かめるだけの部分や、ありふれた式変形（解析に多い）は長くてもよく、長い式変形も 1 行と数える。記号の定義・置き方の準備だけを 1 ステップにせず、それを使う適切なステップの冒頭（`【主張：…】` の前）に書く。主張より前に書いた部分は、段階表示で理由を開く前から見える。hypcheck の項目に「Step N で使った」と書いておくと、段階表示でそのステップの理由を開いたときに「このステップで使った前提」として出る。**読者の記録（2026-10-22）**：段階表示では理由を開くときに「確かめた」「わからなかった」を選び、ステップごとに記録される（`learn.js` の `StepLog`、localStorage `sm_step_progress`）。`【主張】` のないステップでは全文を見せ、その下の「このステップ：確かめた／わからなかった」で記録する（記録が消えないための受け皿。新しい証明には主張を付ける）。「わからなかった」ステップは「要復習」としてそこだけを順に読み直せ、付箋ドックのメニューから該当する定理をまとめて付箋に集められる。記録の形式は `{v:1, items:{"<ラベル>#<ステップ番号>": {s, t, h}}}` で、ログインやサーバー保存を入れるときは `StepLog.load / save` の中身だけを差し替える（記録の鍵がラベルとステップ番号なので、ステップを書き換えると見出し `h` が合わない古い記録は無視される）。
* **`hypcheck`**（各 proof の中の最後。主要な証明には必ず付ける）：
  1. 各前提がどの Step で使われたか。集合論なら、どの公理を使ったか（ZF で済むか、AC が要るか）。
  2. 前提を外したり変えたりしたときの反例。
  3. 本質的でない前提・使わなかった前提・弱められる前提。
* **付属ブロックの置き方**（詳細は `AUTHORING.md` §3.2）：
  * **定理の下**：`intuition` → `example` → `proof`（最後に `hypcheck`）→ `supplement`。`supplement` には一般化、前提を変えた反例、類似の定理、高い視点をまとめる。
  * **定義の下**：`intuition`, `example`。
  * **補題を多数経由する定理**：節の最初に主張を述べ、補題の後に `::: restate {ref="…"}` で再掲してから証明する。
  * 特筆すべきことのない欄は書かない。`remark` は多用しない。
  * 有名で重要な一般化・反例は、別記事の独立した定理にして `supplement` から `\ref` する。
* **高い視点**（圏論・位相・普遍性など）は、本質的なときだけ `supplement` に書く。こじつけない。
* **事実性**：
  * 確実でない主張・文献は書かない。書くなら「〜とされる（未確認）」と明記する。
  * 範囲外の結果は `::: fact` にし、出典は確実に知っている標準的教科書名だけを書く（ページ番号は書かない）。
  * 捏造した文献・年号は絶対に書かない。
* **訳語**：`_claude/TERMS.md` の採用訳を使う。表にない語は、第 3 節の方法で日本語の本での使われ方を調べてから決める。自分で直訳した語を使わない。
  * 例：almost disjoint を「概離散」と訳したのは誤りだった。
  * 訳語が複数流通しているときは、`index` と `keywords` に別訳も入れて検索で引けるようにする。
* **検索用の属性**：主要な定義・定理に `keywords="English name, 別名"` と `index="用語|よみ, …"` を付ける（読みはひらがな）。ページのタイトル行にもラベルと keywords を付ける。
* **数式**（KaTeX で通るもののみ）：
  * 添字は 1 文字でも波括弧で囲む：`a_{n}`。
  * 表の中では `|` の代わりに `\vert` を使う。
  * 長い式はディスプレイ数式にする。
  * `$` 記号そのものは `\$` と書く。
  * 共通マクロ（`\R \N \Z \ZF \ZFC \restr{A} \defeq` など）は `config.js` にある。使う前に `grep -n` で確かめる。

- **ディスプレイ数式の横幅（ユーザー指示 2026-10-01、PDF 化に備えて）**：`$$ … $$` は PC 表示で横スクロールが起きない長さにする（目安：描画幅 690px 以下＝本文 17px で KaTeX 1 行がおよそ 55 文字相当）。はみ出しそうなら `\begin{aligned} … \end{aligned}` で改行する、二列に並べる、あるいは箇条書き・リストに分けて本文中に出す。
- **クラスとメタ圏は太字（ユーザー指示 2026-10-01）**：真のクラス（$\mathbf{V}$, $\mathbf{L}$, $\mathbf{ON}$, $\mathbf{WF}$, $\mathbf{OD}$, $\mathbf{HOD}$、一般のクラス $\mathbf{M}$, $\mathbf{N}$ など）は `\mathbf{…}` で書き、集合と区別する。圏（特に大きな圏・メタ圏：$\mathbf{Set}$, $\mathbf{Grp}$, $\mathbf{Ab}$, $\mathbf{Top}$, $\mathbf{Cat}$, $\mathbf{CAT}$ など）も `\mathbf{…}` で書く。累積階層・構成可能階層の段は集合なので細字で $V_{\alpha}$（Kunen の $R(\alpha)$ はそのまま）, $L_{\alpha}$ と書く（Kunen 1980 の $L(\alpha)$ は使わない。$L(A)$ は相対構成可能性と紛れるため）。$\mathbf{L}[A]$ は集合 $A$ を加えた構成可能宇宙。
- **記法は現代の標準に合わせる（ユーザー指示 2026-10-01）**：参考書の記法が古い場合（例 Kunen 1980 の $L(\alpha)$）、現代の標準的な記法に直し、ページ内で「本書では〇〇と書く」と一言断る。

## 7. 使える環境（一覧。書き方の実例は `template.html`）

* **番号付き**：
  * `axiom`, `definition`, `theorem`, `proposition`, `lemma`, `corollary`
  * `fact`（範囲外の既知の結果）
  * `construction`
  * `counterexample`（有名・重要な反例だけ独立させる）
  * `remark`（独立させる価値のある注意だけ）
  * `problem`（問題）
  * `table`（中に Markdown の表を書く）
* **番号なし**：
  * `notation`（記法）
  * `proof`, `solution`（折りたたみ・目立つ表示）
  * `hypcheck`（proof の中の最後）
  * `intuition`（主張の直後に書くと枠の中に小さく表示）
  * `example`, `supplement`
  * `restate {ref="…"}`（元と同じ番号で再掲）
* **書き方の約束**：
  * `::: 環境名 タイトル {#ラベル keywords="…" index="…"}` で開き、`:::` だけの行で閉じる。入れ子にできる。
  * 付属ブロックの中の環境には番号が付かない。
* **表の記号**：`:yes:` ○、`:no:` ×、`:partial:` △、`:open:` ?。
* **索引**：本文中の索引語は `\index{語|よみ}` で付ける（表示はされない）。定義系の環境では、太字の語が自動で索引語になる。

- **style.css や *.js を直したら、必ず `node tools/build.js` をしてから commit する**。各ページの `<link>`・`<script>` の URL に中身のハッシュ（`?v=…`）が付くので、ビルドしないと古いハッシュのままになり、閲覧者のブラウザに古いファイルが残る（2026-10-10 に影の変更が反映されないように見えた原因）。
- 初回 push の経緯：Cowork ではコンピュータ側で git が使えず（接続フォルダでは削除が禁止）、クラウド側にもリポジトリを接続できなかったため、bundle を作ってユーザーの Mac から push した。
